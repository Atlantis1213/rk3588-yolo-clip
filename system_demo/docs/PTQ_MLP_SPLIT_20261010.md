# CLIP PTQ：MLP 上、下投影拆分对照

后续校准对照已完成：相同精度配置从 normal 改为 KL，准确率59.17%→66.67%，
三context吞吐6.20FPS（同轮normal6.27、FP16为3.81）。仍比FP16低7.5个百分点，
未替换默认模型。详见 `PTQ_KL_CALIBRATION_20261010.md`。

## 本轮结论

完成两个完整 ViT-L/14 候选的构建、板端 120 张验证、实际算子精度及输入位模式核验。
下投影候选有精度收益，因此额外完成同轮 FP16 对照测速；上投影候选没有精度收益，
不追加测速。没有替换默认模型。

当前最值得深挖的是 GELU→MLP 下投影的量化边界，而不是继续扩大 QKV 或上投影的
FP16 保护。但还没有把下投影的权重误差、激活误差和编译器融合变化分别隔离。
本轮没有达到“接近 FP16 精度且约 5 FPS”的联合目标。

## 单变量实验与精度

以此前 59.17% 的混合速度版为起点，一次仅额外保护一种矩阵组：

- 上投影 `c_fc`：1024→4096，共 24 个矩阵。
- 下投影 `c_proj`：4096→1024，共 24 个矩阵。

同一官方参考权重、224 输入、24 个 block、原 120 张校准、120 张验证及六类文本 bank。
继续复用原 Toolkit2 2.3.2 step1 IR，没有重新校准、训练或采用 QAT checkpoint。
LayerNorm、残差、GELU 等原保护策略保持不变；24 个融合 SDPA 保持 INT8。
这些是官方参考 CLIP＋TrashNet 六分类实验，不是历史四分类＋unknown 场景验收。
本轮未使用最终测试集筛选策略。

| 模型/额外 FP16 组 | 正确数/120 | 准确率 | 对 FP16 特征余弦均值 | 文件 MB（十进制） |
| --- | ---: | ---: | ---: | ---: |
| 普通 FP16 参考 | 89 | 74.17% | 1.0000 | 623.05 |
| 原混合速度版 | 71 | 59.17% | 0.7809 | 321.15 |
| 仅恢复 MLP 上投影 | 71 | 59.17% | 0.7781 | 420.93 |
| 仅恢复 MLP 下投影 | 78 | 65.00% | 0.8636 | 422.68 |
| 上下投影均恢复（上一轮） | 83 | 69.17% | 0.8695 | 522.45 |

下投影候选比速度版多 7 张正确，追回 5.83 个百分点；比 FP16 少 11 张正确，
仍低 9.17 个百分点。其 macro-F1 为 0.5889，对 FP16 top1 一致率为 81.67%。
上投影准确率持平并不意味着每张预测相同，也不证明上投影完全不敏感：上下投影
同时恢复比只恢复下投影仍多 5 张正确，存在误差交互和编译器融合变化。
120 张验证只是探索性小样本，不能宣称上述差异已经统计显著或可泛化至实际场景。

## 实际执行与有效性核验

- 两个候选本机 SHA256 与上传模型一致，构建与验证均完成。
- 每个候选的 24 个 `exSDPAttention` 实际均为 INT8 NPU，绕开已复现的混合 FP16
  SDPA 异常；不宣称修复 SDK 或 driver 内部问题。
- 上投影候选：24 个 `c_fc` 为 FLOAT16 NPU，24 个 `c_proj` 仍为 INT8 NPU。
- 下投影候选：24 个 `c_fc` 仍为 INT8 NPU，24 个 `c_proj` 为 FLOAT16 NPU。
- 120 张输入 FP16 位模式与样本顺序均与普通 FP16 基线逐文件一致。
- 下投影候选算子表中的 CPU 项只有 InputOperator、OutputOperator；没有观察到
  LayerNorm、GELU、Attention 等大量 CPU fallback。

实际算子表也解释了为什么不能仅数 FP16 矩阵来预估速度：上投影候选出现
`ConvExSwish` 融合，但 GELU 后仍有 FLOAT16→INT8 转换；下投影候选保留独立的
FP16 `exSwish`，后接 FP16 `ConvAdd`，没有原来 GELU 后的 INT8 输入转换。
因此“恢复一个矩阵组”同时影响 W/A 计算、转换边界和融合方式。
带 perf 收集的逐层 Time(us) 不是独立测速结果，不能跨轮直接相减归因。

此前第 12 层 GELU 的宽量化范围、小激活大量被舍入到零仍是合理线索。
本轮下投影恢复收益与该线索相符，但不是激活误差单独主导的最终证明；不能据此
盲目裁剪大值或把权重 per-channel 当成激活 per-channel 已实现。

## 下投影候选的独立短基准

Runtime 2.3.2 使用工程内隔离库，系统 Runtime 2.3.0、driver 0.9.6 不修改。
串行执行两轮正序/反序，每配置 8 秒；相同固定 FP16 tensor、host 输入，不开启
perf 收集，初始化与热身不计入测速。没有同时运行其它 NPU 任务。

| 配置 | 同轮普通 FP16 | 下投影 FP16 混合版 |
| --- | ---: | ---: |
| 1 context/all 核，FPS 均值 | 2.220 | 2.560 |
| 3 context/spread，FPS 均值 | 3.826 | 4.270 |
| 3 context，两轮 FPS | 3.809 / 3.842 | 4.234 / 4.305 |

三 context 聚合吞吐相对同轮 FP16 提高约 11.6%，不如原速度版此前测得的约 6.25 FPS。
原速度版及整组 MLP 版不是本轮同步重测，不能把跨轮数据当作精确同条件速度排名。
下投影候选三 context 的各 worker 平均 run_ms 约 672–684 ms；
1000/4.27≈234 ms 是聚合完成间隔，不是单张 CLIP 延迟。
以上是 CLIP-only 吞吐，不含 YOLO、摄像头、RGA、DMA 和完整流水线。
分类报告中的历史 mean_run_ms/speed_ratio 字段不用于独立加速结论。

## 下一步优先级

1. 收集原 120 张校准图在各 block 的 `c_proj` 输入分布：按通道范围、主体分位数、
   QDQ 零值比例和重建误差，区分稳定离群通道与样本特异大值。禁止用一张验证快照
   直接决定裁剪阈值，也不读取最终测试集做筛选。
2. 做少量层的下投影保护对照（例如前/中/后各 8 层），每个候选仍检查实际 dtype、
   SDPA 执行及输入一致，再同时验收分类与同轮速度。目标是量化保护的收益/成本排序，
   不是默认宣称减少保护必然能保持精度。
3. 再试 SDK 支持的范围校准或边界精度配置。原 MMSE 未完成，不能写成已经验收；
   针对 GELU 后的量化适配也不能直接照搬此前 LN→linear 的等价通道均衡。
   后者此前已实现但未恢复 INT8 精度，不应将其重新命名为新成果。
4. 只有训练代理能匹配实际 INT8 SDPA 和 MLP 量化边界时再继续 QAT/蒸馏，
   最终以导出后的板端分类与速度为准，不以代理余弦改善替代验收。
