## 一、对照实验实际证明了什么

同一 USB 摄像头、YUYV 640×480、同一模型、YOLO 2 线程、CLIP 4 线程、相同 NPU
核分配和队列容量，开启整图回退。三组各运行 12 秒、重复 3 次，顺序轮换，9 次均完成。

| 配置 | CPU 占用 | YOLO 前处理 | CLIP 前处理 | 完整推理 FPS |
| --- | ---: | ---: | ---: | ---: |
| CPU 图像处理＋标量归一化 | 32.07% | 19.02 ms | 7.12 ms | 3.465 |
| DMA/RGA＋标量归一化 | 16.52% | 19.49 ms | 7.87 ms | 3.424 |
| DMA/RGA＋LUT 归一化 | 11.90% | 10.56 ms | 2.02 ms | 3.425 |

CPU 百分比按“100% 为一个 CPU 核”计算，不是整块板卡的百分比。
这次短测中，组合优化使平均 CPU 占用相对 CPU 基线降低约 62.9%。NPU 计算仍是
吞吐瓶颈，因此不能写“整体推理帧率提升了多少倍”。RGA 单独也未让前处理墙钟更快。

基线每帧处理显式复制原始 YUYV 和 letterbox 图像；DMA 路径消除了这些 CPU 图像复制。
统计到的显式复制量从每轮约 77.3 MB 降为 0，但 CPU 归一化写 tensor、RGA/NPU 内存
读写仍存在，SDK 内部复制不在这个计数范围。

摄像头实际交付约 10 FPS；本次画面未检测出目标，CLIP 使用整图回退。数据用于系统
对照，不是准确率实验。FPS 包含队列排空，延迟从帧出队开始，不包括曝光和 USB 传输。

## 二、为什么 LUT 有效，为什么不影响模型

归一化输入是 uint8 RGB，每个通道只有 256 种值。将原公式和 FP16 位表示提前算出：

```text
YOLO: pixel / 255
CLIP: (pixel / 255 - mean[channel]) / std[channel]
```

运行时用像素值查表，替代逐像素浮点运算和 FP16 转换。当前正确转换的两个模型表
合计3 KiB；为复现历史数据保留另一套legacy表，因此实现总量是6 KiB。
这属于前处理实现优化，不是量化、剪枝、换模型或近似标准化。

同一 CPU 核、500 次计时、3 次重复的独立测量：

| CPU | 归一化任务 | 标量 | LUT |
| --- | --- | ---: | ---: |
| A76 / CPU4 | YOLO 640×640 | 4.380 ms | 0.932 ms |
| A76 / CPU4 | CLIP 224×224 | 0.690 ms | 0.111 ms |
| A55 / CPU0 | YOLO 640×640 | 21.746 ms | 2.991 ms |
| A55 / CPU0 | CLIP 224×224 | 4.068 ms | 0.372 ms |

测试逐通道覆盖全部256种值、带stride的行和输出尾部，scalar/LUT逐位一致。
旧测试只证明相互一致，未验证IEEE正确性；green=250的CLIP输入曾被错误地从接近2.0
转为1.0。当前增加compiler half类型的独立参考及舍入进位、subnormal、tie等边界检查。
默认LUT和scalar均用修正后的转换，legacy选项仅用于旧结果复现。没有声称实现NEON。
gprof 对独立标量工作负载完成采样；它不是整个多线程应用或 NPU 的算子 profile。

## 三、修复了什么资源管理问题

原实现只把输入槽的整数编号放进队列。如果队列已关闭，Push 直接返回，没有调用
释放回调；预处理在入队前抛异常时，也缺少自动归还责任。这是退出/异常路径的
逻辑槽泄漏，不是已经观察到的持续堆内存泄漏。

新实现用 `BufferPool::Lease` 表达所有权：申请、移动到任务、消费、析构归还。
关闭队列拒收、丢弃旧任务、生产/消费异常、队列销毁都能归还。槽状态用 shared_ptr
维持生命周期，Lease 只允许移动；状态不持有 Lease，不形成引用环。

GDB 在原逻辑的隔离复现中捕获异常，堆栈定位到关闭后的 Push，查看到 `free_slots=0`。
修复后的同一关闭场景测试通过；ASan/UBSan、4,000 个并发任务及关闭唤醒测试也通过。
这是有真实工具记录的回归复现，不是声称曾出现生产环境段错误。

5张原测试图片在当前标量/LUT、普通/DMA输入、多Context和串行模式下均与修正后的
scalar参考一致；两个legacy变体单独与旧程序一致。新旧checksum不同不代表回归失败。

## 四、本轮调度与量化的真实成果

修正后固定图片三轮对照：默认配置3.628 FPS/P95约2605ms；1 YOLO adaptive+
3 CLIP spread/per_core gate为3.582 FPS/P95约1734ms。尾延迟降33.45%，吞吐降1.27%，
应讲“减少核争用并改善尾延迟”，不能讲“已经实现5 FPS”。

官方参考模型的120张独立最终测试：FP16为415.87ms/70.83% accuracy，普通INT8为
257.10ms/22.50%。量化约快1.62倍，但精度不可用，自动混合和通道均衡也未通过验证。
目前仍保留原部署模型；MMSE转换本轮中止、未评估。公开六类结果不是原场景准确率。
下一步应先定位逐层误差，再决定手动混合量化或QAT，不是只调整线程数量。

## 面试时建议这样讲

> 我把 YOLO-CLIP 部署到 RK3588，负责 Linux 视频输入和系统推理优化。通过 V4L2
> 导出 DMA-BUF，让 RGA 在共享图像缓冲区中进行缩放和颜色转换；CPU 将归一化结果
> 直接写入 RKNN 的原生 FP16 DMA 输入。不同帧通过两级工作线程和有界队列重叠执行。
> 我做了同摄像头对照，发现优化主要降低 CPU 开销，NPU 计算仍限制吞吐；随后利用
> uint8 输入的有限取值，把归一化改为位级一致的 LUT，并用 GDB、sanitizer 和回归
> 测试验证数值及缓冲区所有权。

能继续追问的重点：

- FD 不是物理地址；CPU 虚拟地址、DMA 地址和缓冲区句柄不同。
- 零拷贝减少 CPU 搬运；图像和 FP16 tensor 使用不同 FD。
- 缓存同步与设备完成同步解决不同问题；当前 RGA 同步完成后才能归还帧。
- 多 Context 提升任务并发机会，不保证单次推理更快。
- round_robin/spread是固定worker核映射；adaptive YOLO通过应用层arbiter选择空闲核，
  不是驱动抢占或硬实时调度。
- 核绑定不是线程优先级；这里没有实现 RTOS 调度。
- 当前板端用 g++ 原生编译，不是已完成的交叉编译方案。
- 原模型训练、ONNX 导出和历史转换配置缺失，不能把未知内容写成完成经历。

## 阅读代码的顺序

1. `src/main.cpp`、`src/pipeline.cpp`：程序入口与线程分工。
2. `include/v4l2_capture.hpp`：DQBUF、EXPBUF、QBUF 与帧生命周期。
3. `include/dma_buffer.hpp`、`rga_preprocess.hpp`：共享缓冲区与硬件图像处理。
4. `include/normalization.hpp`：原公式与 LUT，配合测试理解位级一致性。
5. `include/model_runner.hpp`：Context、核分配、原生布局与输入绑定。
6. `include/buffer_pool.hpp`、`pipeline_queue.hpp`：资源归还和生产消费者同步。
7. `include/npu_arbiter.hpp`：逐核准入、RAII Permit与adaptive请求优先准入。
8. `quantization/README.md`：校准/验证/最终测试划分、转换与速度/精度双评估。

构建和运行方法见 README。详细数据见 `docs/RESULTS.md`，原始结果在 `results/`。
